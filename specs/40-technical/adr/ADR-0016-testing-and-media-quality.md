## Context
The suite's test stack (image-annotator ADRs 0012 and 0014) is Vitest, fast-check, Playwright on
Chromium and WebKit, axe, Lighthouse CI, size and licence gates, all run locally with no code-host
workflows, and a manual Gecko check per release. Clip Maker adds media fidelity (NFR-08), speed
(NFR-04), memory on phones (NFR-05) and browser coverage on phones (NFR-12). Two facts shape the
harness: Playwright's bundled open-source Chromium has no H.264/AAC (proprietary codecs ship only
in the branded browser), and FFmpeg is not installed and, as commonly built, is GPL, which ADR-0001
never allows — so export analysis must not depend on it.

## Decision
1. **Unit and property (Vitest, fast-check)**: MOD-Core rule maths (frame times, RULE-03/05/06/10/12
   cases from the ACs, INV-03/04/06 properties), MOD-Plan (time → source time, weights, text
   opacities), MOD-Project operations and undo round trips, MOD-Keys, rate control and file names;
   DSP against analytic signals: resampler response, WSOLA pitch (440 Hz ± 1 % at 0.25×–4×,
   F-005.AC2), equal-power curves, volume dB (F-011.AC3), true-peak limiter (F-011.AC5 on the
   decoded output), WAV writer; the compositor CPU reference against RULE-08's ramp criteria.
2. **Browser integration (Playwright)**: golden-frame tests render the preview path at export size
   and compare with decoded export frames (NFR-08: frame within 1 frame, ΔE00 on a 24-patch chart);
   clap fixtures for A/V sync; the request log (NFR-01); the host stub (RULE-17); offline; scratch
   inspection after every export kind and after a killed page (F-015.AC7, AC14).
3. **Engines**: Playwright `chromium` runs VP9/Opus fixtures; a `chrome` project
   (`channel: 'chrome'`, the installed branded browser, DEP-34) runs the H.264/AAC paths; `webkit`
   runs what its build supports (SP-codec records which). Gecko desktop, iOS and Android are manual
   (below).
4. **Export analysis without FFmpeg**: tests decode exports with the browser's own decoders and the
   container library (MOD-Container in a test page, or mp4box.js in Node for box inspection: colour
   tags, absence of metadata, moov position). Loudness and true-peak checks are our own TypeScript.
5. **Fixtures**: owner-recorded phone clips (iPhone HEVC SDR and HLG, Android H.264), a 5K screen
   recording, a long-GOP screen recording, WebM/MKV recordings, the audio formats of RULE-01,
   damaged and over-limit files, a 4 GB file (generated by our own fixture script by repeating
   encoded packets, kept outside the repository), a 24-patch chart video and a clap track made by
   our own encoder in the browser. Large fixtures live outside git with checksums in a manifest.
6. **Performance and memory**: NFR-03/04 timings scripted in Chromium on the laptop; on phones,
   the same fixture projects run through a hidden test page measured with remote inspection
   (Safari Web Inspector, Chrome remote debugging), recorded per release candidate.
7. **Manual matrix per release candidate** (NFR-12): Gecko desktop (incl. the MP4 + Opus path),
   the WebKit desktop browser, iOS Safari, Chrome on Android, and the Gecko Android browser
   showing SCR-Unsupported; embedded and standalone; touch pass on both phones (RULE-21).
8. **Accessibility, start-up, size, licences**: axe, Lighthouse with NFR-02's throttling, size gates
   from `architecture.md`, and the licence and dist scans of ADR-0001, unchanged from the suite.

## Alternatives considered
- **FFmpeg/ffprobe for analysis** — the fastest route, but GPL builds are never allowed and it is not
  installed; LGPL-only builds are possible but awkward to obtain. Own analysis is enough.
- **Only the open-source Chromium** — would never exercise H.264/AAC automatically.
- **A cloud device farm** — costs money and uploads fixtures; against the budget and PRN-01's
  spirit for the owner's own footage.

## Consequences
- Using the branded Chrome as a test browser is a dev-only, proprietary-licence tool: an owner
  decision (proposal).
- Phone checks stay manual but scripted; their results are recorded with each release.

## Outcome (spikes, 2026-11-04)
Evidence: all thirteen spikes; owner decisions D-035 (branded Chrome as a dev-only test browser,
approved) and D-037 (reference devices: the MacBook and the owner's iPhone 14 Pro; Android deferred).

**Engines (§3) — corrected premise:**
- Playwright's bundled **Chromium 156 on macOS has H.264 and AAC** (decode and encode), but **no HEVC
  decode**, **SwiftShader software WebGL** (4 fps full chain) and the software H.264 encoder. It runs
  logic and codec e2e, never GPU, timing or HEVC tests.
- The **`chrome` channel** (DEP-34, approved D-035, never shipped) runs HEVC fixtures, GPU fidelity
  and timing.
- **WebKit** e2e that touches OPFS runs in a **persistent** context (the ephemeral one has no OPFS);
  where a sync handle still fails, the export test uses the null sink and says so.
- The Chromium frame e2e re-enables `ThirdPartyStoragePartitioning` (Playwright disables it) so
  same-site sharing is tested as real Chrome behaves.
- Playwright Firefox did not launch on the Mac; Gecko stays manual.

**Oracles and fixtures (§1, §2, §5):**
- **Fidelity**: preview path rendered at export size vs decoded export, frame-matched with ties
  broken toward offset 0; spatial checks skipped on near-black frames (mean luma < 16). Clap fixtures
  are checked against the decoded *source* as baseline; the A/V test expects a 0-sample offset after
  decoding with mediabunny (and CoreAudio, manually).
- **Grade**: grade-fidelity fixtures are **RGB stills** (the photo path; video sources add ΔE00
  0.2–0.4 of their own); the chart and ramp oracle is the CPU reference in float. RULE-08 ramp bars
  per the G3 spec change (high-precision render, Grain 0, Vignette per position; 8-bit outputs by
  reversal ≤ ΔL* 0.5 and ΔE00 ≤ 1).
- **Time-stretch**: the 440 Hz ± 1 % unit test covers all 76 speed steps (≈ 1 s of Node time);
  **WSOLA golden hashes** are valid across engines and are used as oracles.
- **Real phone fixtures are mandatory**: owner iPhone HEVC (SDR, HLG, B-frames, open GOP),
  1080p long clip, Retina screen recording (3420 × 2224); generated H.264 without B-frames hid two
  decoder bugs. Plus a synthetic 5120 × 2880 HEVC, a high-motion + grain fixture (the only one that
  breaks the floors, needed for F-015.AC10), and the 4 GB pair generated by remuxing (never with
  Node's `fs.openAsBlob`, which mis-reports sizes above 4 GiB). Fixtures stay outside git.
- **Exports**: a check that output dimensions are even with the long side a multiple of 16; a
  colour-tag check (`colr` primaries/matrix/transfer/range per ADR-0007); a **player check**
  (QuickTime, Photos, VLC/IINA) of the chart MP4 per release candidate.
- **Scratch**: the F-015.AC7 e2e inspects storage **≥ 10 s** after the save; a two-tab sweep test
  (same-site shared storage) and a killed-page test (AC14).
- **Interruption**: simulated hiding (overridden `visibilityState` + a stalled worker) covers
  ADR-0010's rules (a)–(c) automatically; real lock/app-switch is a manual iPhone check.

**Timing (§6):** NFR-03/04 timings are taken on a **quiet host** with the 1-minute load average
recorded at start, during and end; a run whose load average exceeds the core count is repeated.
Spike timings (loads of 20–200 on 8 cores) are upper bounds.

**Manual matrix (§7) per D-037**: MacBook — Chrome, Safari, Firefox (incl. MP4 H.264 + Opus, D-033);
iPhone 14 Pro — Safari standalone and embedded, touch pass, silent switch, lock/app-switch export,
saves to Files and Photos (share). **Android (Chrome, and Firefox Android showing SCR-Unsupported)
is deferred** until a device is available; NFR-12's Android rows are recorded as not yet verified.
