# Spike SP-mem-phone

Frame: row 8 of the spike table in `architecture-proposal.md` §5. Checks NFR-05 against ADR-0009
(files stay files, bounded caches, phone budget ≤ 600 MB), ADR-0003 (engine and export workers),
ADR-0006 (one `paint`), ADR-0010 (export to an OPFS scratch file) and RULE-02 / D-012 (video above
3840 × 2160, up to 5120 × 2880, is scaled to fit 3840 × 2160). Builds on SP-compositor (decoder pool,
keyframe seek), SP-gpu-color (grade chain + look) and SP-speed (export loop, encoder settings), which
already pass on the iPhone 14 Pro (29.9 fps at 1080p and 4K; export 1.74× real time).

**Question.** Do the NFR-05 fixtures preview and export on the reference phone without the page being
killed, with memory that does not grow with source size?

**Hypothesis.** With sources read as `File`s through mediabunny's `BlobSource`, ≤ 6 decoded frames per
decoder, ≤ 2 active decoders, export written to an OPFS scratch file (not an in-memory buffer) and the
sound decoded in small windows, the page's peak memory is set by the decoded frame pool and the GPU
buffers (4K: 6 frames × 12–25 MB + compositor targets), not by file size or project length:
≤ 600 MB on the phone for every fixture, and the 4 GB source within 10 % of the 100 MB source. The
container index of a long file (sample tables) is the only part that grows with the file: a few MB
per hour of video. The 5K screen recording plays at ≥ 24 fps after scale-down on the GPU.

**Fixtures** (owner clips are read from `~/clip-maker-fixtures/` and never enter git; generated files
live outside git and are deleted afterwards):
1. **10-min 1080p project** — the owner's `HD_IMG_6968.MOV` (1080p portrait HEVC, 3 min 23 s, 351 MB)
   used three times with in-points spread over the file, cross-fades, a look and adjustments, 600 s in all.
2. **2-min project from 4K HEVC** — `HDR_IMG_6966.MOV` (4K HLG) and `NON_HDR_IMG_6967.MOV` (4K SDR),
   13 s each, alternated into 120 s with cross-fades (HDR handled by the SP-hdr shader).
3. **Screen recording above 4K-UHD** — `Screen Recording … .mov` (3420 × 2224 H.264, 26 s): taller than
   2160, so RULE-02's scale-to-fit applies (0.971×). A true 5120 × 2880 file is generated if an encoder
   on the Mac can make one; otherwise 5K is recorded as untested.
4. **4 GB vs 100 MB** — the same 48 s edit (4 × 12 s) made from a 4 GB file and from a 100 MB file.
   Both are generated by remuxing (no re-encode) `HD_IMG_6968.MOV`: the 4 GB file repeats it 12 times
   (≈ 40 min), the 100 MB file is its first ≈ 57 s; the edit's in-points in the 4 GB file are chosen so
   every frame is the same picture as in the 100 MB edit.

Each fixture: **preview** (play 3 × 10 s at real time at start / middle / end incl. a cross-fade, and
30 random seeks across the timeline) then **export** (whole project, H.264 + AAC, 1080p for fixtures 1
and 4, 2160p for 2, scaled size for 3; scratch file in OPFS, deleted after).

**Measures.**
1. Peak memory per fixture and phase. Mac (automated): sum of the browser's process footprints
   (`footprint`/RSS of every browser process, sampled every 0.5 s), and Chrome's JS heap. iPhone (owner):
   Web Inspector → Timelines → Memory on the Mac, peak of the page's total, per fixture; plus the
   in-page proxies below.
2. In-page proxies (every engine): open `VideoFrame`s (counted at output/clone/construct and close),
   peak decoder queue, compositor texture bytes, OPFS bytes written, `performance.memory` where present.
3. Crash/reload detection: a `sessionStorage` beacon is set before each step and cleared after; a page
   load that finds it counts a kill and names the step. Results so far persist in `localStorage`.
4. Crash count over 5 runs per fixture (iPhone, owner).
5. Preview fps (median, and frames shown / frames due) for each fixture, incl. the 5K-class source.
6. 4 GB vs 100 MB: peak memory ratio, and open time (container index read).

**Pass criteria.** 0 kills in 5 runs per fixture on the iPhone; peak ≤ 600 MB (phone); 4 GB peak within
10 % of the 100 MB peak; 5K-class source plays at ≥ 24 fps or is recorded as a known limit.

**Time box.** 2 days of agent work (shared with SP-hdr's page and server).

**Devices / browsers.** Automated: Playwright `chrome` channel and `webkit` on the MacBook (Apple M3,
16 GB), files given to the page through a file input (disk-backed `File`s). Owner: iPhone 14 Pro, iOS
Safari over HTTPS on the LAN (`https://10.254.5.94:846x/`, mkcert certificate, CA already trusted on the
phone). Android deferred (D-037).

**Not built.** The real UI, thumbnails/waveform caches, text bitmaps beyond one title, undo history,
time-stretch, the AudioWorklet preview path (preview here is picture only; the export carries sound,
decoded in windows), the sandboxed frame, GIF and audio-only export, rate control.

### What surprised us
1. **WebKit in Playwright cannot open an OPFS sync access handle** ("unknown transient reason"). The first WebKit
   run fell back to an in-memory output, which grows with the output size. The rerun used a byte-counting null
   sink. Real Safari and iOS must be checked by the owner run: the page records the target (`opfs` /
   `memory`) per task.
2. **The GPU side dominates, not file size or JS.** The JS heap stays at 3–4 MB and open `VideoFrame`s at ≤ 13.
   The 4K project uses 318 MB of compositor textures, because the half-float intermediates are allocated at
   *source* size (3840 × 2160 × 8 B × 2 layers) even when the output or preview is smaller. Chrome's GPU process
   reaches 0.95 GB in the 4K export.
3. **The real-clip decoder bugs** (see SP-hdr): presentation times from the index; open-GOP leading pictures
   skipped; look-ahead 12. Without them WebKit could not seek in the iPhone clips at all.
4. Chrome's browser process grows by about the scratch file size during an export (write-back cache) and
   releases it afterwards. This is not page memory, but it is worth knowing on Android.

### Provisional verdict: **adopt ADR-0009's design (files stay files, bounded pools, OPFS streaming), with amendments**
- Size the grade intermediate to the **placed size on the output** (≤ output size), not the source size. On
  phones, allow the 8-bit intermediate at 4K. This cuts the 4K texture budget from 318 MB to about 80 MB.
- **5K sources are a known limit** (below 24 fps preview). RULE-22's slow-device fallback is to show decoded
  frames as they come; the export is still correct (0.6–0.8× real time).
- The final call on the phone budget waits for the iPhone run.

### Analysis
1. **t1 export failure = the spike's encoder watchdog (spike-code issue, now fixed).**
   - `xwriter.js:72` is the "encoder stalled for 4 s" throw. The H.264 encoder queue (5) stopped draining for more
     than 4 s, with no encoder error.
   - WebKit drops `Error.message` from `stack`, so the page logged only the stack. Fixed: errors now carry
     name + message.
   - The watchdog is now 20 s and the export records the longest gap between encoder outputs (`maxOutGapMs`).
   - Whether iOS pauses the encoder for a few seconds (thermal or media-server contention, about 4.5 min into a
     continuous encode) or stops for good needs a re-run.
   - Implication for MOD-Export either way: a pause of a few seconds is not a failure. Use a long watchdog; on a
     real stall, re-create the encoder from the next keyframe and continue.
2. **t2 `Decoder failure`.**
   - On the Mac both engines run H+S, H+H, S+S and S+S+S 4K HEVC decoders at once, also next to a 4K encoder
     (`results/dec-pw-*-r1.json`: all ok).
   - On iOS the second 4K slot never produced a frame, so the likely cause is iOS refusing a 2nd concurrent 4K
     HEVC decode session. Its HDR session is also doing the tone-mapping. Network reads are less likely: t4 used
     the same path without errors.
   - The new `dec.html` page measures exactly this on the phone: 1–3 decoders, HLG and SDR, with and without the
     encoder, with error messages.
   - Mitigations, ranked:
     - **(a)** a per-device **decoder budget**: on the phone, 1 concurrent 4K decoder. A cross-fade between two 4K
       clips then decodes the outgoing clip's overlap first into a small cache of output-size frames (15 frames ×
       8 MB at 1080 × 1920 = 120 MB), then the incoming clip.
     - **(b)** if a 2nd session fails, fall back to (a) at run time (catch `Decoder failure`, close it, retry
       sequentially).
     - **(c)** WebCodecs cannot decode at a reduced size, so "downscale" only helps after decode.
3. **t3 at 0.21×.** Three costs add up:
   - **Decode at about 100 ms per frame.** On the Mac the same file decodes at 350–570 fps. Over the network, the
     2–3.6 s keyframe spacing means every restart re-reads and re-decodes up to 3.6 s.
   - **Wrapping the canvas as a `VideoFrame` at 3322 × 2160 costs 51 ms per frame.** It scales with output pixels:
     about 12 ms at 1080 × 1920 on this phone (SP-speed).
   - **Preview collapses** (0.1 fps, seek p95 18 s). Once decode is slower than real time, each paced request jumps
     past the decoder, and a restart from the previous keyframe re-decodes the whole GOP.

   Proposals to stay within NFR-04 (which is defined at 1080p):
   - export screen recordings at ≤ 1080p by default (wrap → about 12 ms);
   - in playback, never restart while the target is still ahead of the decoder: decode forward and show the newest
     frame, coarse playback;
   - classify sources that decode below real time as slow (RULE-22) and show the notice.

   `dec.html` records whether the 3420 × 2224 H.264 Main@5.2 stream decodes slowly on iOS from memory (a
   hardware-decoder limit) or only over the network.

### Verdict (updated): **adapt**
- Memory independence holds on the phone: 4 GB = 100 MB, OPFS streaming, no kills.
- Three phone findings need design changes: a decoder budget of 1 concurrent 4K session on iOS until `dec.html`
  says otherwise; long-gap-tolerant encoder handling; slow-source playback without restarts, with exports of such
  sources at ≤ 1080p.
- Peak MB on the phone is still not measured (Web Inspector).
