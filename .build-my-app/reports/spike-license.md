# Spike SP-license (blocking; ends in an owner decision)

**Question.** Is mediabunny (MPL-2.0) correct and small enough on our corpus? What would the permissive path really cost?

**Prototype.** Two adapters behind the MOD-Container interface (specs/40-technical/modules):
- **(A)** mediabunny for both reading and writing.
- **(B)** mp4box.js (BSD-3) to read MP4/MOV, plus mp4-muxer and webm-muxer (MIT) to write.

For (B), list the gaps (WebM/MKV, MP3, Ogg, FLAC and ADTS readers; an Ogg writer) with line-of-code estimates.

**Measure.**
- Corpus pass/fail. The synthetic corpus is generated in-browser and covers:
  - rotation metadata;
  - edit lists;
  - variable frame rate;
  - moov at the end;
  - fragmented MP4;
  - truncated or damaged files.

  Add owner fixtures when they arrive.
- Tree-shaken gzip size of the parts we use.
- Peak memory while reading a 4 GB file (generated by a script, kept outside git).

**Pass.**
- (A) reads 100 % of the corpus.
- (A) writes MP4, WebM, M4A and Ogg files that play in Chrome, Safari and Firefox.
- The parts of (A) we use are ≤ 70 KB gzip.
- A written cost report for (B).
- The result is an **owner decision** (D-003, ADR-0005).

**Time box.** 2 days. **Devices.** Desktop Chrome and Safari, with Firefox for playback checks.

### Corpus and read results (each adapter in Chrome 156 and Playwright WebKit)
How the corpus was made: H.264, AAC, VP9 and Opus were encoded with WebCodecs in Chrome. A small ISO-BMFF writer of my own (`spikes/license/src/gen/bmff.ts`) built the MP4 variants from those samples. Before running the adapters, every synthetic MP4/MOV was checked independently: Chrome's and WebKit's own `<video>` loaded each one and played it to the end (22/22, right sizes and durations). The rest of the corpus came from outside our code:
- Chrome `MediaRecorder` (WebM, MKV, MP4);
- macOS `afconvert` (FLAC, ADTS, M4A) and `avconvert` (Apple-muxed H.264 and HEVC MOV with B-frames);
- an MP3 that ships with macOS.

A read check passes when all of these hold:
- the track counts are right;
- the rotation is right;
- the timestamps are within 1 ms;
- the duration is within tolerance;
- WebCodecs decodes every video packet.

A damaged file passes when nothing hangs and no bogus video packets come out.

| File | A | B |
|---|---|---|
| mp4 faststart, moov-at-end, `qt` brand, co64 | pass | pass |
| rotation 90 / 180 / 270 (tkhd matrix) | pass | pass (needs our own matrix-to-rotation code) |
| edit list trim (media_time = 2 frames) / empty-edit delay 0.5 s | pass | pass (needs our own edit-list code) |
| VFR (17–67 ms frame durations) | pass | pass |
| fragmented MP4 | pass | pass |
| truncated mdat (cut at 60 %) | pass (39/60 frames, all decode) | pass |
| moov missing | pass: returns **no tracks**, does not throw | pass: throws |
| random bytes | pass: throws | pass: throws |
| corrupt `stsz` size | pass: video track with 0 packets | pass: same |
| Chrome MediaRecorder MP4; afconvert M4A; avconvert H.264/HEVC MOV (B-frames) | pass | pass |
| Ogg Opus, WAV, MediaRecorder WebM (VP9+Opus), MKV (H.264+Opus), FLAC, ADTS, MP3 | pass (FLAC decode fails in WebKit only) | **unsupported (gap)** |
| **Total** | **26/26 Chrome, 25/26 WebKit** | **19/26** (the 7 misses are the gap formats) |

Cross-read checks:
- A reads all 7 files written by A and B.
- B reads only the MP4/M4A files. It cannot read WebM or Ogg.

| What | gzip |
|---|---|

| writer: MP4 / WebM / Ogg alone | 34.7 / 23.9 / 16.3 KB |

Neither path fits 70 KB. On size, A and B with all formats come out about the same. The budget in `architecture.md` gives the engine worker 150 KB (container read + codec + engine + compositor). If the writer also lives there, A takes 108 KB of that 150 KB.

### Peak memory reading a 4 GB file (Chrome 156, real `File` from `<input>`)
The test file was 4.0 GiB (4,296,090,238 B): 1 h, 108,000 H.264 samples of 38.7 KB, 168,750 AAC samples, moov first, co64 offsets, a 1.15 MB moov. Each adapter read every packet. The file was made by `run/bigfile.ts` in the session scratchpad and deleted afterwards.

| | open | full read | renderer RSS Δ (peak) | JS heap peak |
|---|---|---|---|---|
| A (mediabunny) | 199 ms | 177 s (I/O-bound) | **+77 MB** | 95 MB |
| B (mp4box + Blob.slice) | 72 ms | 254 s | **+306 MB** | 369 MB |

B's cost comes from mp4box building one rich JS object per sample (276k objects). We would have to compact the sample tables ourselves, which adds to B's own code.

Side finding: in Node 24, `fs.openAsBlob` reports the wrong `size` for files over 4 GiB (it wraps at 32 bits). Any future Node-side fixture tooling should avoid it.

### Path B: cost of the gaps (own code, TypeScript, excluding tests)
The figures are calibrated against two things: mediabunny's own sources (Matroska demuxer + EBML 3,690 lines; Ogg demuxer 1,163; FLAC 820; MP3 567; ADTS 496; WAV 597; Ogg muxer 587; codec-data 3,907) and the working Ogg Opus writer I built in this spike (102 lines including the WAV helper, 1.2 KB gzip).

| Gap | Scope we need | LOC estimate |
|---|---|---|
| WebM/Matroska reader | EBML, unknown-size clusters (MediaRecorder output has no duration or cues, so it needs a full scan), SimpleBlock/BlockGroup, lacing, Cues seek, CodecPrivate → configs for VP8/VP9/AV1/H.264/HEVC/Opus/Vorbis/AAC | 1,500–2,200 |
| Ogg reader | page/CRC, packet reassembly, granule → time, Opus pre-skip, Vorbis headers, bisection seek | 700–1,000 |
| FLAC reader | STREAMINFO, frame sync with CRC-8/16 (FLAC has no packet index), seek table | 500–700 |
| MP3 reader | frame sync, Xing/Info/VBRI duration and seek, ID3v2/v1 skip | 400–550 |
| ADTS reader | header → AudioSpecificConfig, CRC skip, scan-based seek | 250–350 |
| WAV reader (RULE-01, not in the brief's list) | RIFF/fmt/extensible, PCM packetising | 200–300 |
| Ogg Opus writer | streaming pages, granule/pre-skip/end trim (prototype exists) | 200–300 |
| MP4 hardening around mp4box | multi-entry edit lists, negative ctts, compact sample tables (memory), streaming fragmented files, colr/HDR, codec strings, typed errors | 400–600 |
| Shared codec-config helpers | codec strings and descriptions for VP9/AV1/HEVC/Opus/Vorbis/FLAC | 400–600 |
| **Total** | | **≈4,550–6,600 LOC**, plus a similar amount of tests and a fixture set per format |

Effort: at 150–250 tested lines a day, that is 18–44 dev-days, about **4–8 weeks**. ADR-0005 currently estimates 2–3 weeks, which looks low. On top of that comes a permanent burden:
- two **deprecated, frozen** writers (mp4-muxer 1,879 lines, webm-muxer 1,450 lines), which we would have to fork to get any fix;
- six or more readers of our own, sitting exactly where real files break.

The saving is about 0 KB (see Bundle size).

### What surprised me
- mediabunny does **not throw** on a file whose moov is missing. It returns an input with zero tracks. MOD-Container has to turn "no tracks", or "a track with 0 packets", into a typed error.
- Edit lists come back as negative timestamps (−0.067, −0.033, then 0) in **both** paths. So "drop frames before 0" belongs to our decoder/plan code, not the container.
- WebKit's `AudioDecoder` fails on FLAC that Chrome decodes from the same packets. This needs an SP-codec/ADR-0004 follow-up (for example, a fallback for FLAC on Safari).
- On HEVC, mediabunny reports `hev1.…` for an `hvc1` sample entry. Both strings decode, so it does no harm, but worth knowing.
- `avconvert` bakes rotation into the pixels (240×320, rotation 0). Only real iPhone fixtures will exercise the rotation matrix on Apple-made files.
- Size is the criterion A fails, and the permissive path does not fix it.

### Recommendation (an owner decision, not an approval)
Evidence: **adapt A**. Correctness, memory and playback all favour mediabunny. B costs about 4–8 weeks of extra work, keeps two deprecated writers, and lands at about the same size with about 4× the memory.

**Owner decision D-003 / ADR-0005, choose one:**
1. **Approve the MPL-2.0 exception for unmodified, pinned `mediabunny`** (no `@mediabunny/*`), under the conditions already in ADR-0005. The 70 KB container budget then has to change. Options:
   - raise it to about 110 KB;
   - keep the writer out of the always-loaded engine worker (it is about 48 KB). ADR-0001's "no lazy chunks" rule allows a separate export worker that loads at startup, but it would still count toward NFR-10.
2. **Decline, and take the permissive path.** That means:
   - the 4–8 weeks of own readers and an Ogg writer;
   - the deprecated writers;
   - compacting mp4box's sample tables to keep memory down;
   - the same size problem.

Whichever you choose:
- add "no tracks / 0 packets → typed error" to MOD-Container;
- leave negative-timestamp trimming in MOD-Codec/MOD-Plan;
- revisit WebKit FLAC decoding in SP-codec.

**Still open:**
- owner phone fixtures (iPhone HEVC/HLG, Android, OBS MKV);
- manual playback in real Safari and Firefox;
- WebKit memory at 4 GB (only Chrome was measured).
